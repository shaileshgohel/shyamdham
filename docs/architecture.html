01

Tech stack

One Node process serves pages, handles form submissions and talks to the database. There is no separate API server and no third-party service in the request path.

Architecture

Top to bottom: the browser, the single Next.js process on Render, and the database. Solid arrows are requests; the dotted line marks files generated on the way out.

03

Request lifecycle

  1. The middleware only checks that the sd_session cookie exists. It never touches the database, so it stays cheap.
  2. Every page and action calls requirePage or requirePermission, which loads the session, confirms the user is still active and checks the role's right for that module and verb.
  3. A write runs in one Prisma transaction: validate with Zod, take the next financial-year number from Counter, write the record, append the AuditLog row with field-level changes.
  4. Money never changes shape after it is written. Receipts and vouchers are cancelled with a reason and stay in the ledger; the database rejects any other update or delete.
  5. Balances, reports and stock counts are computed from vouchers and stock movements each time. No running total is stored, so nothing can drift.

05

Integrity rules enforced in the database

These hold even for someone connected directly with psql, which is what the end-to-end suite checks.

TableTriggerRule
AuditLogaudit_log_no_update_delete
audit_log_no_truncate		Append-only. No update, delete or truncate.
Vouchervoucher_ledger_guard
voucher_no_truncate		Only status, cancelReason, cancelledAt and cancelledById may change, once, from ACTIVE to CANCELLED. No delete.

donation_no_truncate		Same cancel-only rule as vouchers.
StockMovementstock_movement_append_onlyNo update or delete. A wrong count is corrected with a new ADJUST row that carries a reason.
06

Document numbers

Every number is taken from the Counter table inside the writing transaction, so two clerks working at once never receive the same one. All series except family numbers restart each financial year, April to March.
